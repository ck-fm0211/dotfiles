## 発見した計画問題パターン

### 1. 2案併記タスクは実装者が判断できない

タスク 1.1（gcloud の curl|bash 廃止）が「Homebrew 管理 or SHA256 検証付き」と両案を併記していた。
Homebrew 化を選ぶと install_gcloud.sh 自体が不要になり、CI の install-gcloud ステップも削除対象になるため、
実装量が大きく異なる。

**ルール:** 2案以上が併記されているタスクは revise_required フラグを立てて方針決定を先行させること。

### 2. 課題説明がコードの実態と乖離していると誤実装につながる

タスク 1.3 は「既定で ~/.aws/ を削除する」という説明だったが、実スクリプトは y/N 確認後に削除していた。
問題の本質は「--purge フラグなしで削除コードパスに到達する設計」。

**ルール:** セキュリティ系タスクのレビューでは必ず実スクリプトを読んで課題説明の正確性を検証する。

### 3. git config はシンボリックリンクで即時展開されるため個人情報が含まれる場合は高優先度

`.config/git/config` に `user.name` / `user.email` がハードコードされており、
別人が `make link` すると即座にその人の Git コミット者が変わる副作用が発生する。
Plans.md では Phase 3（中優先）に分類されていたが、Phase 1 相当の緊急度がある。

**ルール:** シンボリックリンクで展開されるファイルに個人情報が含まれる場合は最優先タスクに昇格。

### 4. DoD がない「完了状態のタスク」はタスクではなく運用ルール

タスク 5.4（完了タスクのアーカイブ）は「作業完了時に都度行う」性質のもので、
独立タスクとして管理すると永続的に TODO に残り続ける。

**ルール:** 単発作業でなく継続的なメンテナンス操作は、タスクではなく Plans.md の冒頭注記や CONTRIBUTING に記載する。

### 5. mise の "lts" 指定は "latest" と同じ問題

`node = "lts"` は「現時点の最新 LTS」を意味し、再現性がない。
Plans.md では `python/go/terraform = "latest"` のみを指摘していたが、node も同じ問題。

**ルール:** バージョン固定タスクのスコープに "lts" 指定も含めること。
